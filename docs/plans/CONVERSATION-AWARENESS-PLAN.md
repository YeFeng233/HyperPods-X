# HyperPods-X 对话感知适配计划书

版本：v0.6 · 日期：2026-10-26 · 状态：独立音轨衰减听感通过，轻声识别灵敏度待解决

实施更新：已移除精确 ROM 指纹门禁，4.0.5 桥接检查通过，并取得真实对话通知。`MAY_DUCK` 两次申请、释放均成功，但系统因“允许多个应用同时播放音频”而跳过降音，用户确认音量无变化。用户明确要求保留此系统设置，因此改为通过已有小米蓝牙宿主，对目标耳机的媒体音轨附加独立 VolumeShaper。用户确认“音量变化正常，没有跳变”，进一步反馈为说话音量足够大时响应及时。计时版测得开始事件到提交 5～24 ms、结束事件到提交 3～6 ms；尚未找到可验证的检测灵敏度参数，轻声识别、后台及中断恢复仍待验收。

目标设备：Xiaomi 17 Pro Max / HyperOS 4 / AirPods 5，沿用包名 `com.hyper.podsrx`、libxposed API 102 与 Miuix 界面。

## 1. 建议方案与交付目标

建议在现有“对话感知”开关上补齐真实事件处理和媒体联动：佩戴者开始讲话时降低正在播放的媒体音量，对话结束后解除降音。识别来源为耳机通过 AACP 上报的状态，手机不录音，也不运行语音识别。

实施先验证两个事实：本副耳机是否稳定上报对话事件，以及它在 Android 连接下是否已经自行降低媒体音量。如果耳机侧已完整处理，就直接使用其能力；只有实际缺少媒体降音时，才验证 Android 音频焦点的临时降音方案。一次对话只使用一种降音路径。

首版以音乐、常用视频播放器和后台使用为验收对象。播客自动暂停、手动结束对话、单耳模式作为分别验证的扩展项。人声增强与临时聆听模式由耳机固件负责，不能仅凭媒体音量降低就声称完整复现苹果体验。

### ROM 差异处理

原精确 ROM 门禁位于系统弹窗、设置入口、空间音频桥接的共同入口。按用户的最新要求，实施改为取消版本号限制，通过现有包名、进程和运行时接口检查尝试加载；已补充原生卡片回调的异常回退。缺少接口时保留系统原流程，不把取消门禁等同于所有 ROM 均已验证。

对话事件与普通应用侧媒体联动可以独立验证，但“与原生弹窗、动态头追同时正常”的交付结论必须建立在 4.0.5 回归通过之后。目前已确认宿主重新加载后的桥接与能力检查；原生弹窗、持续姿态和对话降音的联合效果仍需回归。

### 灵敏度调查与计时边界

苹果的[对话感知说明](https://support.apple.com/en-sg/104979)列出自动降低、恢复媒体音量及手动结束对话，没有给出讲话检测阈值调节。LibrePods `main` 的 `CONVERSATION_DETECT_CONFIG` 为 `0x28`，现有调用按布尔值启用或关闭；本机 alpha.3 的布尔序列化同样使用 `1 / 2`。本机当前回读为 `1,0,0,0`。对这两个参考实现的检查没有找到可验证的灵敏度字段，不能因此断言固件内部不存在阈值。[参考控制定义](https://github.com/librepods-org/librepods/blob/89356c08cea3db0b6b54792d9329d09a87cc85fa/android/app/src/main/java/me/kavishdevar/librepods/bluetooth/AACPManager.kt)

当前在已知最早开始状态 `1` 即提交衰减，不等待状态 `2` 或下一次心跳。保留 `3` 为活动状态，`4` 和本轮新见的 `11` 作为未分类观察；没有以猜测状态含义的方式提前恢复。计时字段 `startSubmitLatencyMs / stopSubmitLatencyMs` 是事件接收至宿主完成提交的差值，`startAckLatencyMs / stopAckLatencyMs` 包括回执调度，均不代表耳机识别或声学端到端延迟。无有效时间戳时记为 `-1`，非事件清理另标 `cleanup`。

## 3. 协议依据与待验证项

苹果目前的支持资料将 AirPods 5 列入对话感知适用设备，并描述了讲话后降低媒体音量、增强面前人声及结束后恢复的行为。这说明产品层面有该能力，不代表本机 Android 链路已经具备全部行为。[苹果功能说明](https://support.apple.com/en-sg/104979)

LibrePods 的公开实现把设置与实时通知分开处理：

| 内容 | 上游及当前项目中的依据 | 本项目拟采用的处理 |
| --- | --- | --- |
| 配置开关 | Control ID `0x28`；当前项目以 `1` 开、`2` 关 | 沿用已验证的读写与确认机制 |
| 实时事件 | AACP opcode `0x4B` | 新增独立事件类型，不将配置回读当作讲话事件 |
| 常见报文 | LibrePods main 校验 10 字节、前缀 `04 00 04 00 4B 00 02 00`，读取索引 9；alpha.3 仍取 payload 索引 3 | 当前真机已收到 subtype 1；保留长度、子类型与连接代次校验 |
| 开始/活跃状态 | LibrePods main 使用 `1、2`；本机 2.0.0-alpha.3 还处理 `3`，本次真机均已出现 | 使用 `1、2、3` 映射；状态机开始计数不是降音听感的验收结果 |
| 结束状态 | LibrePods main 使用 `6、8、9`；本机 2.0.0-alpha.3 还处理 `7`，本次真机均已出现 | 使用 `6、7、8、9` 映射，后续验证实际释放与恢复 |
| 其他状态 | 本次真机还收到 `4`，尚无充分依据解释其完整语义 | 保留原值，不猜测开始/结束，也不无限延长降音 |

依据：[LibrePods AACP 定义](https://github.com/librepods-org/librepods/blob/main/android/app/src/main/java/me/kavishdevar/librepods/bluetooth/AACPManager.kt)、[报文识别](https://github.com/librepods-org/librepods/blob/89356c08cea3db0b6b54792d9329d09a87cc85fa/android/app/src/main/java/me/kavishdevar/librepods/data/Packets.kt)、[事件处理](https://github.com/librepods-org/librepods/blob/main/android/app/src/main/java/me/kavishdevar/librepods/services/AirPodsService.kt)。资料读取日期为 2026-10-26。本机 alpha.3 的 `i` / `n52` 提供事件解析依据，`yw1` 提供扩展状态映射；APK 版本、校验值和具体来源见 [第三方说明](../../THIRD_PARTY.md)。真机已确认这些状态出现，但完整检测语义与媒体效果仍需对照验证。

本机 alpha.3 的 `i.f` / `j.d` / `h70` / `k` 使用 AACP 1.3 握手（第七字节 `03`）、`D7 00 00 00 00 00 00 00` source capabilities、全量通知订阅及 200 ms 初始化间隔。当前试验实现已按这些依据调整。未发现额外的对话感知专用 capability bit；`FF` 试验没有明确收益，不能用它解释后续事件恢复。其 `v4` / `yn` 型号表也将 A3441 列入对话感知能力集合。

Wireshark 的社区协议解析器将 `0x4B` 内容解释为两字节小端长度、子类型和后续数据。因此分帧应处理长度及半包、粘包，而不是直接在任意输入块的第十字节取状态。常见长度为 2 的报文总长为 10；其他长度和子类型需保留诊断后再开放。[协议解析依据](https://github.com/pabloaul/apple-wireshark/blob/main/plugins/aacp/aacp_parse_message.lua)

## 4. 实现结构

```text
现有单一 AACP 连接
    → 有界分帧与对话事件解析
    → 对话状态机
    → 佩戴、媒体路由、通话及开关条件检查
    → 耳机自行降音 / Android 临时降音（二选一）
    → 结束或中断时释放本轮操作
```

### 4.1 连接与事件解析

继续复用 `PodsService` 的控制连接、通知订阅和读循环，不额外建立抢占耳机控制权的连接。新增 `Event.Conversation` 与有界解析；同时检查 opcode 高字节、长度字段、子类型、状态及所属连接代次。

全量通知订阅下已取得首批事件，下一步复核普通重连后能否稳定接收，并确认是否需要特定控制所有权状态。此次经历宿主刷新、控制权／姿态采样、取消校准及重连，尚不能把其中任一步骤视为唯一必要条件。不能因没有事件就反复抢占连接、重写身份或重置配对。与 `0x17` 真实姿态报文共用通道时，必须保持双方分帧正确。

诊断仅记录单调时钟、连接代次、报文长度、子类型、状态值和处理结果。不记录声音、谈话内容、耳机身份密钥或用户设备标识；原始有限协议样本只留在本机诊断目录。

### 4.2 对话状态机

拟使用“关闭、等待条件、就绪、对话中、恢复中”五种状态，由单一执行队列处理事件和清理。进入媒体降音需同时满足：功能启用、配置已确认、当前控制连接有效、有耳佩戴、媒体确实输出到本副耳机、无通话占用，并且收到已验证的开始事件。

重复开始事件不得反复申请焦点或叠加降音；重复结束事件可安全忽略。旧连接事件、未知状态、关闭期间的事件不触发新的降音。重新连接后等待新配置与佩戴报告，不能恢复上次残留的“对话中”。

结束、关闭功能、摘下双耳、入盒、切换输出、控制断开、进入通话及服务退出均触发清理。增加最长持有保护，具体时限由第一阶段的事件周期决定：先查明耳机是只发边沿还是持续上报，不能用任意短超时替代正常结束事件，也不能用持续姿态包为对话无限续期。

### 4.3 媒体降音路径

| 路径 | 采用条件 | 验收要求 |
| --- | --- | --- |
| 耳机自行处理 | 关闭手机降音代码时，仍能稳定观察到耳机降音与恢复 | 保留耳机效果，不再叠加手机降音 |
| Android 音频焦点 | 耳机没有完成媒体降音，且目标播放器与后台条件允许 | 验证临时降音、释放、手动音量操作及播放器兼容性 |
| 其他媒体控制方案 | 前两条不能满足用户常用播放器 | 单独分析后调整方案，不自动改成全局音量反复写入 |

`AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK` 已完成否定性验证：目标 HyperOS 的多应用同时播放规则会忽略本次 MEDIA/MUSIC 请求。用户要求保留该设置，因此停止使用焦点方案，不通过改成无关的导航或通话用途来绕过用户选择。标准焦点机制的适用条件与播放器例外见 [Android 音频焦点说明](https://developer.android.com/media/optimize/audio-focus)。

替代实现使用独立的 `ConversationWire` / `ConversationAudioHost` / `ConversationBridge`，复用已有宿主、签名权限及绑定设备验证。宿主只处理实际输出设备地址匹配目标耳机的 `USAGE_MEDIA` 音轨，未知路由或不支持的播放器跳过。对音轨附加本模块专属 VolumeShaper，结束时恢复该附加增益；不改系统媒体档位，不重设播放器原有音量，不发送播放、暂停键。

宿主与头追拥有独立会话。START、心跳、STOP 使用 owner Binder 与会话 ID，拒绝旧会话清理新操作。显式结束、客户端死亡、心跳超时、路由变化、通话及最长 60 秒限制都触发恢复。曲线采用 `CLOCK_TIME`，自身在期限内回到增益 1，使宿主进程异常退出时仍有音轨侧恢复上限；新出现音轨只使用本轮剩余期限。IPC 未报错只代表已提交操作，仍须验证真实听感和恢复。

首轮音轨方案已通过用户听感确认，但仍需验证延迟、手动暂停、手动音量与后台场景。START/STOP 的 Binder 回执只代表提交结果，不能单独当作声学确认。LibrePods 参考实现采用修改 `STREAM_MUSIC` 的方式；本项目避免反复改动手机总音量，因此不直接照搬该恢复策略。[LibrePods 媒体处理](https://github.com/librepods-org/librepods/blob/main/android/app/src/main/java/me/kavishdevar/librepods/utils/MediaController.kt)

### 4.4 Android 17 的后台条件

本机 targetSdk 为 37。Android 17 对后台音频操作增加限制，前台服务还涉及 while-in-use 能力；单看“服务正在前台运行”不足以证明焦点请求一定有效。后台启动、开机恢复与用户在前台开启服务必须分别验证。[Android 17 后台音频说明](https://developer.android.com/about/versions/17/changes/bg-audio)

优先沿用现有 `connectedDevice` 前台服务，从用户在应用内启用功能的操作建立有效生命周期。检查焦点返回值与 `AudioHardening` 诊断；若后台恢复后能力不足，提供一次可理解的恢复操作，不在页面上假称已正常工作。测试覆盖切到桌面、锁屏和服务重建，不通过关闭系统音频限制来取得验收结果。

### 4.5 与现有功能协调

| 功能 | 协调要求 |
| --- | --- |
| 自动入耳检测 | 对话结束只解除本功能的降音，不发送通用“播放”按键。若摘耳已暂停，结束对话不能使其续播。播放器因焦点自行暂停/恢复也需联合验证 |
| 动态头部追踪 | 共用控制通道，保留真实姿态与校准数据；对话中持续追踪，退出不遗留传感器或媒体资源 |
| 设置回读 | 当前写入后约 1.2 秒未确认会重连，此过程会结束头追。切换 `0x28` 前先比较当前值，避免无效重写；需要重连时统一清理，并协调恢复用户仍然要求且条件满足的功能，不复用旧姿态或旧对话状态 |
| 聆听模式 | 观察耳机是否自行进入/退出临时通透；不在每次讲话时强写 `0x0D`。用户在对话中切换模式时，不用旧快照覆盖 |
| 个性化音量 | 分别测试开/关组合，区分其持续调整与对话临时降音；不能把两项效果叠加后误判成故障或成功 |
| 原生弹窗与电量 | 不因说话事件触发开盖卡片；电量和 BLE 开盖处理继续使用原逻辑 |

首版不增加 LSPosed 作用域。保留 `com.android.settings` 与 `com.xiaomi.bluetooth`；无需为手机麦克风、无障碍服务或通知读取新增授权。

## 5. 界面方案

在现有“功能设置”中保留一个“对话感知”开关，使用 Miuix 当前卡片样式。副标题简短显示“等待耳机连接”“等待确认”“已就绪”“正在交谈”或明确的失败原因，区分设备配置与媒体联动状态。

常态说明为“说话时降低媒体音量，对话结束后恢复”。尚未确认设备支持、未完成配置回读或后台条件不足时，不显示已经就绪。关闭功能立即清理本地降音，再处理设备写入与确认；写入失败要明确反馈。

升级保留原有配置，测试前记录实际值；未完成真机验收前保留实验状态说明。首版不增加降音百分比滑杆、讲话灵敏度、状态码面板或单独的校准流程。对话感知使用耳机自身检测，不沿用空间音频的三轴校准。

## 6. 分阶段实施与通过条件

当前进度：P0 已完成版本门禁移除、宿主桥接与能力检查；P1 已取得首批真实事件并确认本轮没有可闻的自动降音，稳定性、关闭对照及周围人讲话对照仍待补齐。P2 开始验证临时焦点；P3 的解析、状态机与 UI 随试验包增量接入，不代表整阶段或 P4 已完成。

| 阶段 | 工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0：基线 | 复核 4.0.5 系统适配；重新连接并读取 `0x28`、佩戴、聆听模式和当前媒体路由；记录原配置 | 可重现当前基线，明确系统桥接是否需要兼容更新 |
| P1：真实事件 | 构建仅增加协议诊断的包；低音量媒体下采集本人讲话、停止、周围讲话及关闭功能的对照 | 确认事件格式与语义，分清耳机是否已经自行降音 |
| P2：媒体路径验证 | 按 P1 选择耳机路径或音频焦点；先在常用音乐播放器测试，再验证后台与锁屏 | 实际听感下降并恢复，音量操作符合预期；不能只看日志成功 |
| P3：功能接入 | 加入有界状态机、清理和简洁 UI；处理配置回读重连及入耳检测协调 | 单项与联合回归通过，异常时无残留降音和误续播 |
| P4：交付 | 生成优化测试 APK、校验值与测试记录，区分支持/部分支持/未验证播放器 | 用户确认真实交谈体验；测试结束恢复记录的原配置 |

若后续 P1 复测再次没有真实事件，分析订阅、所有权和设备状态，不用手机录音生成替代事件。若 P2 焦点路径不适用，输出失败证据与替代方案后再决定实现，不提前宣布全播放器兼容。

## 7. 验收清单

| 场景 | 通过标准 |
| --- | --- |
| 正常讲话/结束 | 至少 10 次连续对照，真实事件与听感对应；每轮恢复，无降音累积 |
| 仅周围人讲话 | 验证是否误触；分别记录耳机检测结果与软件处理，不假称手机能辨别讲话者 |
| 持续对话 | 测试超过短句的连续交谈、停顿及再次讲话；保护超时不造成反复音量跳动 |
| 功能关闭 | 无新的手机侧降音；未结束的操作及时清理 |
| 手动音量和暂停 | 音量键及耳机滑动的最新选择保留；手动暂停后不因对话结束而误续播 |
| 摘下一只/双耳/入盒 | 与自动入耳检测共同工作；不把暂停责任错误交给对话功能 |
| 断开与重连 | 断连、关闭蓝牙、服务重建后无旧对话重放、无长期降音 |
| 输出切换 | 切到手机扬声器或其他耳机时释放操作，不影响新输出 |
| 通话、语音助手 | 通话期间不干预通话音量；其他焦点请求优先，中断后无迟到的降音 |
| 前台、桌面、锁屏 | 相同功能实际成立；记录 Android 17 生命周期限制及恢复方式 |
| 不同播放器 | 至少覆盖用户常用音乐和视频播放器；播客单独记录，不能概括成全应用支持 |
| 动态头追同时开启 | 真实姿态持续有效；讲话、结束及开关回读后不遗留失效会话 |
| 原功能 | 4.0.5 下设置入口、开盖弹窗、三部件电量及现有设置回读无回归 |

测量目标：收到有效开始事件后，软件侧在 200 ms 内开始处理；收到结束事件或明确中断后，在 500 ms 内发起释放。以上是开发目标，不是本轮测量结论；讲话识别和自然结束的等待时间由耳机算法决定，系统淡入淡出另行记录。

自动验证重点为长度越界、拆包/粘包、与姿态包混合、重复/未知/旧事件、关闭竞态、焦点失败/丢失、断连清理与暂停冲突。实际降音和后台有效性必须通过真机补足。构建时运行协议/应用相关测试、Lint 和优化测试包构建。

## 8. 后续需要的硬件配合与交付物

已进入联调，后续分轮提示操作：佩戴双耳并保持连接；播放低音量媒体后正常讲话数秒再停顿；对话中调一次音量、暂停一次；随后测试摘耳、锁屏和动态头追组合。每轮开始前说明动作及预计时长；当前首先需要确认临时焦点路径是否实际降音并正常恢复。

交付包括源代码、优化测试 APK 与 SHA-256、事件映射说明、播放器兼容清单和恢复验证记录。保留现有 0.4.2 包与耳机/头追校准数据；回退须考虑 Android 版本码限制，不以卸载清数据作为默认步骤。

实施继续遵循“真实耳机事件 + 优先耳机自处理、必要时验证 Android 临时降音”的路线；首版维持一个简洁开关，并将 4.0.5 兼容核验、后台能力与现有功能联合回归作为交付条件。已收到事件只说明协议阶段取得进展，当前尚未达到对话感知功能的交付标准。
