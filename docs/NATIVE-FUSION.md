# HyperOS 融合设备中心

本适配来自 NEORUAA/HyperPods-X 的 PR #1，源提交 `ae9fa5ec8028e94e0dbbf8243228387756edd78e`，集成到 HyperPods-X 0.4.9。它使用系统已有的耳机卡片，和 App 内选择 miuix 或 iOS 风格相互独立。

## 入口与作用域

LSPosed 保留“系统设置”（`com.android.settings`）和“小米蓝牙”（`com.xiaomi.bluetooth`），另勾选“设备互联”（`com.milink.service`）。首次启用或从不支持热重载的旧版升级时，需要重新启动相应宿主，或重启手机。App 的“更多设置 → 启用系统适配”可请求作用域。

在系统中连接已绑定的 AirPods 5 或 AirPods Pro 3，并将它设为当前媒体输出，再打开融合设备中心的耳机卡片。电量来自模块实际收到的耳机数据；未读取或失效的值不伪装成 0% 或满电。

设备互联的 `HeadSetsDetail.a0()` 在服务连上和每次状态更新（消息 1005）时，都会用 `C()` → `x0.a(type, vidPid)` 选图并 `setImageResource`；所有 AirPods 共用一张 `circulate_airpods_headset_icon`，不区分型号。模块在 `a0()` 执行后，把已绑定目标卡片的 `headsetIcon` 换成本 App 对应型号的双耳图（见 [ARTWORK-SOURCES.md](ARTWORK-SOURCES.md)），按型号解码一次后复用。卡片按固定高度、fitCenter 显示图片，系统图片是 560 px 见方、耳机横跨约 298 px 的画布，因此模块把几乎无留白的双耳图居中补成同比例的正方形透明画布，避免显示过大。`C()` 仍返回上述系统图片，只在模块图片载入失败时作为回退；找不到 `a0()` 或唯一的 ImageView 字段时只跳过换图，控制功能照常。热重载后为已打开的卡片重绑控件时，同样优先换成模块图片，载入失败才使用系统图片。

## 控制路径

- 聆听模式从左到右为关闭、通透、自适应、降噪，与 miuix 首页一致。操作转发到模块现有 AACP 会话，回读确认后更新选中项；显示顺序不改变原生模式编号和点击处理。
- 系统空间音频按钮关闭时选择关闭，开启时选择固定；App 的三态选择器继续提供头部追踪与校准。两端显示同一个空间音频状态。
- 音量和响铃查找保留系统控件与处理路径，响铃的实际声音效果需要独立验证。
- “更多设置”打开绑定设备的 HyperPods-X 页面，并使用当前选定的界面风格。

型号识别由 App 与宿主共用的 [`HeadsetModels`](../core/wire/src/main/java/com/hyper/podsrx/hook/HeadsetModels.java) 统一维护。2026-10-29 核对 Apple [中国](https://support.apple.com/zh-cn/109525)、[美国](https://support.apple.com/en-us/109525)和[日本](https://support.apple.com/ja-jp/109525)官方型号资料，三地列出的耳机型号一致，全部纳入识别及原生控制的型号范围：

| 产品 | 耳机型号 |
| --- | --- |
| AirPods 5 | `A3531`、`A3532`、`A3533` |
| AirPods 5（配无线充电盒） | `A3439`、`A3440`、`A3441` |
| AirPods Pro 3 | `A3063`、`A3064`、`A3065` |

Apple 该页面没有给出各型号与销售国家或地区的一一对应关系，因此不按地区或包装料号过滤。充电盒自身的型号不作为耳机 AACP 会话型号加入控制白名单；聆听模式等具体功能仍以耳机实际回读为准，不因型号入表而伪造能力。本次仅补齐型号范围，未运行测试或新增真机验证。

只匹配模块已经绑定、已连接并报告上述型号的耳机，状态快照有效期为 30 秒；其他设备继续使用原生实现。设置回读所需的主动重连期间，在音频路由仍有效的前提下，最多保留 5 秒已确认的展示状态，并停用控制写入；重新收到聆听模式后恢复。真实断开或超过期限不会继续保持可操作状态。`1B20` 仅为系统卡片的展示模板，不写入系统耳机身份表，也不允许系统另开一条 AACP 连接。

四个模式按钮创建一次后保留，收到模式、等待状态或回读结果时只调整选中与可用状态。自适应模式不再经过原生未知模式的隐藏分支，普通状态变化也不会重复重排按钮或触发卡片高度动画。

命令先经过原生内容提供者的权限及包签名检查，再通过模块签发的 PendingIntent 进入未导出的接收器。接收器校验设备地址、型号、连接状态、命令取值和 2 秒时效。密钥不进入共享偏好。宿主类或接口不匹配时，该适配会记录失败，其他模块功能继续运行。

## 验证范围

本轮编译与真机结果统一记录在 [测试报告](TEST-REPORT.md)。原作者的截图说明提供了设计参考，不等同于本次在当前手机上的功能验证。

## 卡片可打开，但图片和控制项一起退回默认

这种情况需要区分 Hook 安装失败和耳机识别状态未刷新。2026-10-28 的实机日志中，面板适配已经 `ready`，但设备互联发现阶段得到 `checkIsAirPods=false`、空 `deviceId` 和 `activeHeadset=null`，界面使用 `circulate_bluetooth_card_more_setting` 的通用蓝牙卡，而非 `HeadSetsDetail`。电量心跳只能更新已有耳机对象，不能保证重新建立首次识别失败的对象。

先确保 App 已连接、型号已回读，再重新加载小米蓝牙宿主，随后重新进入或重新加载设备互联，让发现流程重新识别耳机。更新模块后可通过重启手机完成相关宿主的重新加载。本次重新加载后，系统报告模板 `1B20`，卡片的 `Native panel target: matched=true`，双耳图片、四档聆听模式与空间音频入口恢复显示。

蓝牙宿主会记录 `Native fusion target`，卡片记录 `Native panel target`，仅在匹配状态变化时输出设备是否匹配、型号、连接及心跳状态，不输出实际地址。root/shell 的 `content call` 与设备互联的调用身份不同，单独的 `Result:null` 不足以判断桥接失败；应以真实客户端的识别日志和卡片匹配结果为准。

## 模块热重载

本开发版使用 libxposed API 102 的 `autoHotReload=true`、`onHotReloading` 与 `onHotReloaded`。覆盖安装时框架通知已注入的宿主，模块先注销旧接收器、偏好监听、任务和线程，再安装新代 Hook；已打开的设备卡片重新绑定四档按钮及图片。日志接收器在 Application 创建完成后注册，以保证卸载时使用相同的 Context 身份。

App 在框架服务连接或作用域批准后先等待自动更新，仅对仍为 `STALE` 的已注入目标补交一次请求。尝试记录按安装时间和版本号区分，所以相同版本号覆盖安装仍会检查；失败、更新中或超时不会循环重试。状态和结果写入 `HyperPods-Reload`，并随“导出日志”保存。

头追、对话降音或卡片写命令正在执行时拒绝重载，旧会话继续运行。预检查只暂停新会话准入，保留现有会话的心跳、姿态与停止请求。卸载成功的旧音频 Binder 明确返回已退役，App 重新发现接口并最多重试一次。

首次启用时尚未注入的宿主、旧模块拒绝卸载、清理或重新安装失败，仍需要重启相应宿主。热重载只更新模块代码，不保证重建系统此前误识别成通用蓝牙卡的耳机对象；卡片识别异常仍按上一节排查。API 契约见 [模块生命周期](https://libxposed.github.io/api/io/github/libxposed/api/XposedModuleInterface.html)。

## 手动重启作用域

两种风格的“更多设置”都有“重启作用域”。点击后由 Root 管理器授权，仅处理模块当前已授权的系统设置、小米蓝牙和设备互联。拒绝或授权超时不会提交重启命令；操作期间按钮禁用，完成后显示实际结果，并将 `HyperPods-Restart` 记录放入导出日志。

重启按该用户的包 UID、声明进程名和 PID 精确匹配，发送信号前再次核对身份。不会按共用 UID 整组结束进程，也不会对系统蓝牙栈执行重启。蓝牙与设备互联通过原有后台服务恢复，必要时临时允许后台启动 10 秒，不更改永久电池设置；设置旧进程结束后，下次打开页面加载新模块。后台服务未恢复时会单独提示，退出旧进程不等同于全部服务就绪。

“系统蓝牙入口”这一重复授权行已移除；“系统蓝牙设置”仍用于打开系统页面。三个作用域统一从“启用系统适配”（iOS 风格为“系统原生适配”）申请。
