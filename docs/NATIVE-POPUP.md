# HyperOS 原生 AirPods 弹窗与超级岛适配方案

HyperPods-X 深度复用了 HyperOS 系统内置的原生快连弹窗与超级岛组件，实现开合盖原生动画与实时双耳电量展示。

---

## 1. 复用的系统组件

- **宿主进程**：`com.xiaomi.bluetooth`（小米蓝牙）
- **动态快连插件**：`preloadedFeature`（系统路径预置快连组件）
- **原生底部弹窗**：`MiuiFastConnectActivity`（运行于 `com.xiaomi.bluetooth:ui` 进程），由 `MiuiAirPodsFastConnectController` 驱动系统布局 `fc_airpods_dialog`。
- **原生超级岛**：调用系统 AirPods 适配器通用的 `StatusBarManager.setStatus(1, "strong_toast_action", bundle)` 入口，由 SystemUI 中的 `DeviceNotificationListenerImpl` 负责最终渲染。

---

## 2. 状态中心与开合盖检测机制

### 2.1 蓝牙广播截获与中继
- **系统行为**：HyperOS 蓝牙栈在识别出 Apple 专属广播（`07 19` 邻近配对广播）后，会拦截并直接分发至小米蓝牙的 `MiuiBluetoothContentProvider`，导致普通应用的实时 BLE 扫描无法接收到这部分广播；如果仅依赖普通批量扫描（Batch Scan），延迟可高达 1.4～15 秒。
- **中继方案**：模块挂接小米蓝牙宿主中该 Provider 的 `call` 方法，拦截蓝牙 UID 发来的邻近配对数据，通过高优先级前台广播快速转发至模块状态中心（Hub），单次开合盖广播的到达延迟从秒级骤降至 3～50 ms。
- **身份验证与解密**：状态中心使用本地存储的 IRK 验证蓝牙广播地址，并通过 ENC 密钥解密 Payload，确保仅响应已绑定的正品耳机，杜绝误弹与伪造。

### 2.2 弹窗调度与生命周期优化
- **进程复用（跳过冷启动）**：系统原生的 `MiuiFastConnectActivity.onDestroy` 会强制调用 `System.exit(0)` 杀掉 `:ui` 进程，导致每次开盖都需经历约 0.6 秒的冷启动。模块在已绑定耳机的弹窗关闭时，通过设置 `mBaseRunning` 跳过进程退出，后续开盖直接复用进程，弹窗响应时间缩短至 50～150 ms。
- **防抖与即时收回**：
  - **开盖**：收到首条合法开盖广播后立即拉起弹窗，并配合 300 ms 的信号稳定期确认回连状态；若期间盒盖关闭则立即撤回。
  - **合盖**：检测到合盖广播后立即发送关闭信号，驱动弹窗滑出收起，彻底解决原生系统合盖后需等待 8 秒超时才关闭的迟钝问题。
- **状态同步**：系统因耳机回连自行打开弹窗时，模块会接管其布局，同步写入最新电量与耳机型号，避免显示未知电量或重绘冲突。

## 3. 视觉展现与超级岛适配

### 3.1 底部弹窗
- 保留系统原生圆角卡片、毛玻璃底色及入场/退场动画；
- 完整展示左右耳与充电盒的独立电量；若充电盒暂未上报新数据，优先展示带“上次”标记的缓存电量，未获取时显示“—”，避免错误显示为 0%；
- 根据耳机型号自动加载匹配的高清耳机渲染图（支持 AirPods 5 与 AirPods Pro 3）。

### 3.2 超级岛
- 在其他应用前台时触发超级岛，左右两侧分别呈现对应单耳的独立图标与百分比电量，不展示充电盒；
- 左右单耳素材经精确居中与无缝裁切处理，保证在超级岛药丸内对齐且不产生多余留白；
- 超级岛当前作为轻量电量通知，点击交互以系统通知流为准。

## 4. 优化实测数据

在 Xiaomi 17 Pro Max（AirPods Pro 3）上的实测对比：

| 阶段 | 传统第三方扫描方案 | HyperPods-X 宿主状态中心方案 |
| --- | --- | --- |
| **广播到达延迟** | 1.4 ～ 15 秒（连接后甚至收不到合盖） | **3 ～ 50 毫秒**（全生命周期实时中继） |
| **开盖至弹窗呈现** | 约 1.1 秒以上（冷启动缓慢） | **约 0.05 ～ 0.15 秒**（常驻进程复用） |
| **合盖至弹窗收回** | 约 8 秒（依赖系统超时关闭） | **约 0.6 秒**（含 0.32 秒原生滑出动画） |
| **开合防抖与复现** | 10 秒内重复开盖被系统抑制 | **每次开盖均能即时响应** |
