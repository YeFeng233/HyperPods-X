# HyperOS 4 原生 AirPods 界面适配

目标为 DEVICE-BASELINE.md 中的单台真机，日期 2026-10-22。

## 复用的系统实现

- `com.xiaomi.bluetooth`，版本 17 / code 37。
- 动态快连插件 `preloadedFeature`，已安装路径版本 `1.14@1`；本次分析 APK 的 SHA-256 为 `90EC6AF9792D82350E44E1E01C05B6B74C6C1429765AA15D947C6200661A315A`。
- 底部弹窗：`MiuiFastConnectActivity`，进程 `com.xiaomi.bluetooth:ui`，由 `MiuiAirPodsFastConnectController` 与系统 `fc_airpods_dialog` 布局显示。
- 超级岛：使用系统 AirPods 适配器相同的 `StatusBarManager.setStatus(1, "strong_toast_action", bundle)` 入口，经 SystemUI 的 `DeviceNotificationListenerImpl` / `DeviceNotificationHandlerImpl` 渲染。

真实开盖事件仍由本 App 进行 IRK 校验、解密和按采集时间排序；广播来源与确认时序见下文“开盖检测与弹窗时序”。
本次没有将设备身份伪装成 AirPods Pro 3，也没有依赖名称匹配附近耳机。

## 请求与数据

App 通过只允许本应用签名发送的有序广播请求“小米蓝牙”宿主，携带有效期 1 秒的时间戳和本应用创建的不可变 PendingIntent。
在桌面选择系统底部弹窗，在其他应用中选择系统超级岛；两者均可单独预览。

底部弹窗保留系统窗口、布局及关闭行为，适配已绑定设备的真实电量和产品图片。
只有带有效 App 标识且设备地址匹配远程偏好的弹窗，才会使用适配数据；其他原生 AirPods 界面继续走系统实现。
不向系统提供 IRK/ENC 密钥，不修改系统蓝牙库。真实开盖的弹窗保留系统的回连回调，由 `CachedBluetoothDevice.connect(true)` 恢复 A2DP/HFP；预览只做展示，不连接设备；两者都不建立第二条 AACP 控制连接。系统因耳机回连自行打开的弹窗被接管后，同样保留系统自身的连接流程。
未确认的电量显示未知值，避免系统原布局将音频断开时的电量写成 0%。

底部卡片始终保留充电盒图片和电量区域，不随盒体缺少新上报或耳机未充电而隐藏。实时盒体电量优先显示；仅有缓存时显示百分比并标注“上次”，完全未知时显示“—”。历史值只用于带标记的卡片展示，超级岛仍仅展示左右耳。

0.4.7 起，超级岛左区显示左耳图片和左耳百分比，右区显示右耳百分比和右耳图片，不展示充电盒。
左右电量分别读取 `native_left` / `native_right`；有效范围为 0～100，未知值显示“—”，不拼接成双耳组合文字。
构建任务从每张原透明双耳图生成 `<型号>_left` / `<型号>_right`（目前为 `airpods5` 与 `airpodspro3`），保留原图高度和像素，并去掉两只耳机之间的透明间隙。
产品图片由系统按本 App 的 drawable 名称读取；双耳、充电盒及单耳资源明确保留，避免优化构建删除仅由外部宿主使用的图片。

### 按型号选图（2026-10-28）

底部弹窗、超级岛和 App 内的图片与名称由 `HeadsetModels` 决定：优先用 AACP 会话报告的型号号码，尚未连上时用已验证广播中的型号码（AirPods Pro 3 为 `0x2720`）。App 把最近一次广播型号码保存在本地，并作为 `panel_product` 发布；开盖请求同时带上 `model` 与 `product`。系统因回连自行打开的弹窗没有这两个参数，改读已发布的状态。未识别的型号沿用 AirPods 5 图片。

## 开盖检测与弹窗时序（2026-10-28）

### 广播来源

- 系统蓝牙栈识别出 Apple 广播后，不再分发给普通 App 的实时扫描，而是通过 `onAppleScanResult` 直接交给小米蓝牙的 `MiuiBluetoothContentProvider`。第三方 App 只能从批量扫描拿到这些广播；批量扫描在 Android 中最快 5 秒报告一次，并按 5、5、10、10、20 秒逐级退避，只在亮屏时重置。实测开合盖消息晚到 1.4～15 秒。
- 小米蓝牙自己的扫描在耳机连上后会停止，直到弹窗流程结束才恢复，因此系统看不到耳机连接期间的合盖广播；系统的开盖弹窗靠耳机回连（HFP 进入连接中）触发，合盖收回靠断开连接。
- 模块在小米蓝牙主进程挂接该 provider 的 `call`，只接受蓝牙 UID 发来的调用，将其中的 `07 19` 邻近配对消息以前台广播转发给 App（`LidRelayHost` / `LidWire`）。同一地址内容不变时 1 秒内只转发一次；转发带 `FLAG_RECEIVER_FOREGROUND`，避免普通优先级广播约 500 ms 的延迟。App 只接受 `getSentFromUid()` 为蓝牙 UID 的转发，并照常用 IRK 校验地址、用 ENC 密钥解密。
- App 在原有批量扫描之外保持一个同样过滤 `07 19` 的实时扫描。它本身收不到 Apple 结果，用途是让芯片持续接收，系统暂停自己的扫描时转发通道也不中断。
- 息屏时两个扫描都停止，并清除盒盖状态；亮屏后重新开始。亮屏 1.5 秒内收到的第一份盒盖状态只作为基准，不弹窗。

### 弹窗时序

- 收到第一份开盖消息立即请求弹窗，弹窗进程的启动与 300 ms 稳定期并行；稳定期只用于触发回连和记录日志。盒盖在此期间晃回关闭时，弹窗随即收回。每次“合上 → 打开”都会重新弹出；“耳机已连接”卡片仍保留 10 秒冷却，并且要等控制通道报告电量、本次会话的 A2DP 也已连上后才显示。
- 收到合盖消息后，App 发送 `CLOSE_NATIVE_POPUP`（受本应用签名权限保护），弹窗进程中已绑定耳机的弹窗立即滑出；0.7 秒和 1.5 秒后在盒盖仍关闭时再发一次，覆盖弹窗尚未开始监听的情况。原有 8 秒自动关闭作为兜底保留。
- 系统 `MiuiFastConnectActivity.onDestroy` 每次都会 `System.exit(0)`，导致每次开盖都要冷启动 `:ui` 进程并重新注入模块（约 0.6 s）。对已绑定耳机的弹窗，模块在 `onDestroy` 前设置系统用于“已有弹窗”分支的 `mBaseRunning`，跳过退出，后续开盖复用进程。找不到该字段时只跳过保活，其余适配照常安装。
- 系统因耳机回连自行打开的弹窗（`hyperpods_adopted`）不再关闭，改为写入模块最新发布的电量、连接状态与名称并沿用模块内容；该弹窗显示时，模块的开盖请求不再叠加第二个。
- 跳过系统“正在连接”超级岛时，同时移除它排队的 10 秒 `MSG_CONNECT_FAIL_SHOW_ISLAND` 检查。否则合盖后检查触发，系统会把弹窗再次拉起。
- 耳机出盒后正在回连时，弹窗绑定快连服务会读到 HFP“连接中”，系统控制器随即用 `setConnectLessLayout` 重画“正在连接”，与模块的电量布局及两套渐变动画叠在一起。模块发起或接管的弹窗跳过这一“连接中”布局，连接失败与重置提示照常显示，系统回连本身不受影响。

### 实测（AirPods Pro 3 / A3065，屏幕常亮）

| | 改动前 | 改动后 |
|---|---|---|
| 开盖、合盖消息到达 App | 1.4～15 s；耳机连接期间收不到合盖 | 3～50 ms，连接期间同样收到 |
| 开盖到弹窗显示 | 约 1.1 s 以上 | 冷启动约 0.4 s，复用进程约 0.05～0.15 s |
| 合盖到弹窗收回 | 弹出约 8 s 后由定时器关闭 | 约 0.6 s，其中 0.32 s 为滑出动画 |
| 合上再打开 | 10 秒内不再弹出 | 每次弹出 |

## 当前验证

已在实际设备截图中看到原生底部弹窗及超级岛，确认 App 首页图片显示；预览标题明确标记，未知电量显示“—”。

桌面真实开合盖回归已通过：用户针对“合盖误弹、开盖原生底部弹窗、左右耳和盒体电量”回复“无误弹，显示正常”；日志同时记录经过身份验证的开盖稳定事件和系统弹窗启动。
App 前台真实开盖回归通过：用户回复“有正常显示”，日志在 06:51:54 与 06:52:16 记录真实开盖稳定后提交 SystemUI。

超级岛点击实测没有跳转。此 ROM 的 `island_param` 路径将图片、文字和时长传给岛组件，没有转发请求中的 `target`；当前将超级岛作为电量提示，高级设置仍使用 App 或系统蓝牙详情的入口。此项未标记为点击功能通过。
完整结果记入 TEST-REPORT.md。

2026-10-28 在目标真机安装 0.4.7、重新加载小米蓝牙宿主后，超级岛预览截图确认左右单耳分居两端，各自显示真实的 100%，无充电盒图标或电量。开盖触发仍提交同一系统模板。系统字体、布局与时长继续由原生组件处理。
