# HyperPods-X 真机联调记录

日期：2026-10-22（Asia/Hong_Kong）。适配基线见 [DEVICE-BASELINE.md](DEVICE-BASELINE.md)。
这是开发版的已验证结果，不代表开发方案中的全部目标已经完成。本文不包含用户的耳机名称、地址、序列号或身份密钥；原始联调数据留在应用私有目录及忽略目录，不随交付物发布。

## 构建与模块

- Debug、经 R8 优化的 Release 与 deviceTest APK 均可构建。
- 当前 0.3.2 纯协议测试 **24 项通过，0 失败**：原有 15 项协议/广播测试，加 9 项姿态协议、四元数、校准、传感器描述、回执错误与分帧边界测试。
- 当前 Android lint：**0 错误、16 条非阻断提醒**。
- 真机 LSPosed 服务与模块加载均确认 **API 102**。
- Settings 实际页面为 `DeviceProfilesSettings`，注入入口可点击进入 App，摘要显示左耳、右耳和盒体电量。
- 0.2.0 作用域为 `com.android.settings` 与 `com.xiaomi.bluetooth`，分别承载蓝牙高级入口和原生耳机界面；不修改原生蓝牙库或全局 VendorID。
- 优化后的 deviceTest 包已安装回归，框架日志再次确认 API 102 加载，实际蓝牙详情页再次显示入口和电量。R8 显式保留模块类与生命周期入口，元数据与 scope 文件存在，debug 测试接收器不在优化包中。

有效参数接入常规服务后，使用目标广播过滤、连接失败后被动等待开盖/ACL 事件。
在**未开启隔离诊断、App 已退到桌面**的实际开合盖测试中，累计收到 15 条匹配广播，
日志记录了打开、关闭、再次打开及真实开盖卡片。用户明确回复：**“出现‘充电盒已打开’卡片”**。
该验证闭环与初期连接提示的失败分开记录。

增强扫描结束后的低功耗待机测试中，用户确认开盖卡片可显示，但反馈合盖也曾弹出一次。
对应日志显示，同一批回调在几十毫秒内交错处理开、关状态，并在最终状态已关闭时仍显示开盖卡片。
修复采用 `ScanResult.timestampNanos` 排序与新旧检查，丢弃超过 15 秒的旧帧；
开盖状态在串行事件循环中稳定 900ms 才确认，关闭帧取消待显示请求，UI 执行时再次检查当前盒盖状态。
相关协议回归通过；第一轮修复包复验中，用户确认合盖没有卡片、开盖有“耳机已连接”卡片。
本轮没有收到新的开盖广播，不能据此标记广播开盖复验通过。
移除连接已存在时留下的无效开盖重连请求，并取消 30 秒后切换低功耗扫描：
当前常规服务持续使用已取得目标广播的低延迟扫描和厂商过滤，后台功耗仍需长时间测量。
最终包日志在 06:09:26、06:10:05 两次确认开盖稳定并显示“充电盒已打开”；
对应的关闭广播没有触发开盖卡片。用户最终目视确认：**“合盖没有卡片，开盖卡片标题：充电盒已打开”**。
本轮修复与广播开盖复验通过，手机保留此优化测试包。
